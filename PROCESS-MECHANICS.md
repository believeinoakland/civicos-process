## 1. The index

The process is carried out by one tool, `tools/proc.mjs` (one command per step: it checks the state it needs, does the whole step, writes it to git and verifies, or refuses naming what is missing and writes nothing, P16), its hooks `tools/hooks.mjs` (what must never happen, in code: a PreToolUse refusal names the route; a Stop refusal names what is owed), the checks under `checks/` (`checks/README.md`), and the few files `proc shims` writes into a product (`PRODUCT-SUPPLIES.md`). Every rule names its principle; a rulebook holds the rule and its check, the design file the mechanism and its measurements.

## 2. What no other text says

**The tranche cycle, in one line per step** (P10, P12; the rules are PLN, INT, REL): `proc tranche open` fast-forwards the fixed branch `tranche` to `main` and makes the first round's plan current (`build/plan/current.md`, written only by the tool, durable); `proc epoch open` makes the state branch; `proc takeover` records BOB; `proc layer start` opens each job (branch, START, draft PR, session), lowest layer first; the jobs complete, are reviewed by judgment and merged by the tool as green results arrive; `proc layer close` regenerates the artifacts, runs every check and archives the layer's sessions; the next layer starts at once; `proc round close` archives the plan whole (`build/plan/archive/<T>-R<n>.md`) and makes `next.md` current if it exists, else the round after is the completion round or the tranche closes; `proc tranche close` merges `main` in, runs the checks, marks the plan CLOSING and prints the one PR to `main`; `proc tranche merged` records it; `proc epoch close` deletes the state branch. The next round opens the moment this one closes, if its plan has entries; the completion round is the last (PLN 7). Paying old debt down is planned work, an entry like any other (P7, P19).

**The plan's lines.** `build/plan/current.md` holds the entries by layer and module and nothing transient; the plan's Status (`OPEN | CLOSING | CLOSED · BOB #<n> · <session>`), Owed and Layers lines live on the state branch as `plan.md`, written only by the tool.

**The requirements' format** (P5; the rule is REQ 3). A Purpose is one or two sentences; a Provides entry gives the service's name, inputs, outputs and errors, and its behaviour, every statement under a permanent id `R<n>`. A user of a module reads its public part only (Purpose and Provides); the private part (Uses, Invariants, Satisfies, Suggestions) is read by the module's own job. A job reads the Purpose of each module it uses (a job for a new module, of every earlier module) beside the services its entries touch (BLD 1).

**Legacy modules** (P4, P7; the rule is REQ 9). A target module's code may sit in several legacy modules: its `from` in `build/modules.json` names each, and the extraction rule holds in each. A legacy module earlier in the order than the target cannot import it; there the job only removes, and the code that needs the moved part reaches it from a module later than the target. Extraction runs bottom-up, a layer at a time; source-anchored tests are retired with the legacy code they anchor on.

**Sessions started by a routine.** A session started by a scheduled task (`create_new_session_on_fire`) has no parent and lacks the connectors and the session tools; it is never ROOT, a BOB, a job or a lane (SES 1).

**The checks** (P7; the rules are BLD 4–5, INT 2–3, REQ 1, 3). `checks/README.md` holds each check's text: architecture, coverage, ownership, format, channels, words, fixtures. The gate (`JOB-LIFE.md` §4) runs them scoped to the module on every pull request and `proc layer close` runs them once over the product.

**The cross-account channel** (P13; the rule is REP 3; the check is `checks/channels.mjs`). Sessions on two accounts cannot message each other, so a correspondent on another account (Bob's design session, or the process on a second account during a move) is reached by a mailbox in git: each side appends to its own outbox on its own mail branch and reads what it has not read when it looks. `build/channels.md` on `main` has one row per participant (`name`, `account`, `mail branch`, `outbox`, an optional `letter`, `writes`); it changes only when a participant is added or a branch renamed. An outbox holds a Writer line (`**Writer** · <name> · <session id> · <account> · since <date>`, rewritten by a successor at takeover), one cursor line per correspondent (`**Read** · handled <NAME> <L><n>`) and numbered append-only entries (`## <L><n> · <KIND>[ · re <L><n>] · <date> · <session id> · <account>`); to send, append to your own outbox and push; to receive, fetch the other side's branch, read every entry past your cursor in order, act on each, then move the cursor; never write another's outbox, never put a secret in an entry. Kinds: `NOTICE` (a ruling of Bob's recorded: number, gist, where folded), `QUESTION` and `ANSWER` (`re U2`), `DEFER`, `HANDOFF` (work a ruling owes the other side), `MERGE`, `ACK`. Each side reads its correspondents' outboxes at takeover, at the backstop checks it already runs, before recording a ruling of Bob's, and when Bob says "check the channel"; no timer is armed for it. The design session never writes `build/` (save its own registry row through its PR); BOB never edits the design session's files and keeps its text in a merge conflict. DEC numbers are the design session's alone (the next free across `main` and its open branch, posted as a `NOTICE`; if `main` gains the number first, the branch renumbers); K numbers are BOB's alone. When Bob rules on a UX question through BOB, BOB posts a `NOTICE`; a DEC's `owed:` work reaches BOB as a `HANDOFF`, folded into requirements once the DEC is on `main` or Bob names it, answered with the K that folds it. `tools/mail.mjs` carries the channel (`xwriter`, `xpost`, `xinbox`, `xdone`, `xcheck`) from any checkout without touching the working tree, reading the registry from the product's `origin/main`; sessions never write an outbox by hand.

**Certifying a revision** (P3; the rule is GOV 5). A revision is certified on the toy product (`dryrun/`, seeded onto a repository of its own, `believeinoakland/neoprocess-dryrun`) run by real sessions exactly as a product tranche runs: every row of its certification is proven by what git and GitHub show, never by a session's report, or names why it can only be proven in a product run with the check that will prove it. Each flaw the run finds is fixed in the tool with a test before the run goes on (`lane-neoprocess/DRYRUN.md` §4). The run's record and its rows are kept (`dryrun/N1/`).
