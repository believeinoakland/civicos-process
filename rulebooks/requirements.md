# REQ · Requirements & architecture · the design BOB owns, written so a module can be built and proven from it

In force from 2026-10-29, certified on N1. At most ten rules, one screen, each checkable. Tags: YOURS (Bob's policy) or BOB'S; CODE names what enforces it, TEXT means nothing does.

1. Modules stand in one total order in `build/modules.json`, each in exactly one layer, a layer's modules adjacent and lower layers first; a module uses only earlier modules, each declared in `uses`, and every import matches. (P4) BOB'S · CODE: the architecture check (imports, one owner per file); TEXT for the layer order.
2. Bob decides adding, removing or reordering layers and capability modules, and what a requirement means; BOB decides every other part of the architecture (boundaries, splits, `uses` edges, order within a layer, file ownership, helper and legacy modules) and reports it done. (P4, P5, P17; K1257, K2008) YOURS · TEXT.
3. Each `build/requirements/<module>.md` has a public part (Purpose; Provides: each service's interface and behaviour) and a private part (Uses as `<module>.<service>`, earlier modules only; Invariants; Satisfies, citing the canon by section; Suggestions, which bind nothing), every statement under a permanent id `R<n>`. (P5, P15) BOB'S · CODE: the format check (files parse, referenced ids exist).
4. A requirement states behaviour at the interface, concise and unambiguous, and never requires an implementation. BOB removes an ambiguity a module or user finds by rewriting the text to state the service as it is. (P5, P7) BOB'S · TEXT.
5. A retired id is marked retired or "moved to <module> R<n>" and is never reused; a requirement planned and not yet met carries `*(not yet met: T<n>)*` until the job that meets it strikes the mark in its own commit. (P5, P15; K624; JOB-LIFE §3) BOB'S · CODE: `proc job complete` strikes the mark and the ownership check allows that edit alone; TEXT for reuse.
6. A change to a requirement goes to Bob only by DES 1's test (what the product does for its users, unanswered by the canon), with explanation, options and a recommendation, the ask `NEEDS BOB` until he decides; any other change, an edge case or a service's detail, is BOB's or the lane's, decided from the canon and reported; a wording-only fix needs no job. (P5, P17; DESIGN-STAGE §2; Bob, 29 Oct) YOURS · CODE: `proc ask close` refuses until the requirement is folded.
7. A decision is written in its home before the requester is answered: the canon design by its lane, the requirement and the rulebook by BOB, a requirement citing the canon section and a lane decision as `L-<ID>-<n>`, never a ruling number. For a changed service BOB adds an entry for each user module: a CHANGE to its running job, else its START, else the completion round. (P5, P9, P10, P15; DESIGN-STAGE §1-3) BOB'S · CODE: `proc ask close`.
8. A module is sized so one session reads whole its code, its requirements and the services of its uses that its entries touch; BOB splits one too large, copy then delete in one tranche, the old module delegating, the new one entering `modules.json` with empty `paths` and `tests` until its job completes. (P6; K624, K3268) BOB'S · CODE: `proc status` lists `SIZE` for a reading set over its limit.
9. A legacy module is marked `legacy` and placed after the modules extracted from it; the target's job may in its files only remove the moved code and rewire callers by an import and the lines using it, the net change a removal, and BOB reads every added line before merging; a legacy module retires when empty. (P4, P7) BOB'S · CODE: the ownership check lists every added line.
10. Every plan opens with the legacy census: each legacy module with the entry that retires it or the hard reason it stays. While a tranche runs BOB drafts each coming extraction's map (`build/extraction/<module>.md`; snapshot code is judged only by the requirements) and the next requirements on the tranche branch, never touching a running job's module or the requirements it reads. (P18, P19; K1007) BOB'S · TEXT.
