# neoProcess requirements

**Status** · ACCEPTED by Bob, 30 Oct 2026 ("I accept the requirements"), after his review and seven rounds of his corrections in the session of neoProcess #20, following Civicsmith's first day under the process. Nothing here is code yet: each requirement is met by a job of the process built under itself (MNT-1), proven by fixture and then by a layer run (MNT-7). The P11 change in §14 is approved as wording here; the principles file changes only on Bob's word to change it (GOV 3).

**Why this document exists.** The process asks every product module for requirements, each proven by a test, and never had its own. Its tool grew to about 6,900 lines in two days with 255 fixture tests and no requirement to test against; its rules were enforced by hooks that pattern-matched command text; and its fixes were made in reaction, 28 in one day, while the product ran. Bob, 30 Oct: the requirements "need to expand to encompass everything learned from the civicsmith mess ... as well as the additional requirements we should be able to anticipate", "firmly grounded in our knowledge, experience, and foresight".

**How to read a requirement.** Each has a permanent id, a statement of behaviour, a **Source** and a **Proof**. A Source is one of: *measured* (a number or an event read from the record, with where); *issue n* (a flaw report on the process repository, 30 Oct 2026, read whole); *dry run n* (a flaw the toy run found on 29 Oct, `lane-neoprocess/DRYRUN.md` §4); *Bob, date* (his words); *foresight* (not yet seen; the reasoning is given). A Proof is one of: *fixture* (a unit test on the tool), *layer run* (the next layer, or part of one, run under the change on a real project; MNT-7), *audit* (read after the fact from transcripts or the record). A requirement proven only by fixture is not yet proven; the process version as a whole is *certified* only by MNT-7's mark.

**What changes from today's design, in one paragraph.** The hooks go: nothing refuses an act or holds a turn, and nothing judges a message by model before Bob sees it. No step of the process depends on archiving a session, switching off a scheduled task, or a session starting its own successor. A module's gate is its own suite and the checks, run once, in CI, and never by a session. No byte limit is fixed in code; budgets come from the model's window and from measurement, and an overrun is reported, never refused. A project picks up a process change only when it is stopped: at a declared stop mid-layer, where each unmerged job is given the chance to complete or is abandoned, or at a layer boundary when a newer process version exists and the architecture session chooses to take it; otherwise the next layer starts at once. A change is proven incrementally: fixture tests first, then the next layer, or part of one, running under it on the real project; when the version is new or in doubt the architecture session starts a subset of the layer first, so the work at risk is bounded. The process version earns its certification mark only once it has carried a real product through a full tranche, a deployment and a walk of the release. The process is built under itself. (Bob, 30 Oct.)

## 1. Architecture of the process as a product

Proposed for Bob's approval (P4). The tool today is one file; it becomes modules in one total order, each with the requirements below, each with its own tests, built by jobs like any product. Layers lower first; a module uses only earlier ones.

| layer | module | what it provides |
| --- | --- | --- |
| 1 · foundations | `platform` | what the hosting platform does and refuses, measured and dated; the acts the process may depend on; tokens and grants |
| 1 | `record` | the git record: branches, the state branch, durable and transient files, one writer per file; `status` reads it |
| 2 · the shape of a product | `architecture` | the module order, layers, `uses`; the checks on code (architecture, ownership, format, words, coverage, fixtures) |
| 2 | `requirements` | requirement files, ids, marks; what is a test and what is a measurement |
| 3 · the work | `planning` | tranches, rounds, layers, entries, the completion round; pause and resume |
| 3 | `jobs` | a job's branch, pull request, START, take-in, report, completion, hold |
| 3 | `gate` | the CI gate: the module's suite, the checks, the artifacts; what triggers it |
| 3 | `integration` | review, merge, layer close, tranche close, release |
| 4 · the people | `sessions` | roles, who starts whom, refresh, reading sets and budgets, models, usage |
| 4 | `messages` | between sessions, and to Bob |
| 5 · the process itself | `maintenance` | flaw reports and replies; process versions and releases; certification; the process built under itself |
| 5 | `shims` | what a product receives and onboarding |

## 2. `platform` · what the platform does and refuses

**Purpose.** Everything the process does runs in Claude Code cloud sessions against GitHub through an agent proxy. The platform refuses things, unpredictably in one place, and the process must stand on what is known to pass (Bob, 30 Oct: "CC has its flaws which need to be recorded and worked around so that neoprocess and development generally can be done on footing that's known").

- **PLT-1** · The module keeps one table of platform constraints: each a measured fact with its date, how often it was measured, the evidence, and the workaround the process uses. Nothing elsewhere in the process depends on a platform behaviour that is not a row. *Source:* Bob, 30 Oct; the act table `tools/acts.md` did this for refusals but tried to predict a classifier (PLT-2). *Proof:* fixture (every platform call the tool prints is a row); audit (a refusal not in the table is a flaw report).
- **PLT-2** · The process depends on no act whose outcome the auto-mode permission classifier decides case by case. Today that means: no step requires `archive_session`, `update_trigger`, `delete_trigger`, `interrupt_session` or an edit of a settings file. *Source:* measured: `archive_session` refused as "External System Writes" or "Interfere With Workloads" at 14:35Z, 16:15Z (two) and 17:1xZ, passed at 14:1xZ and 16:4xZ for the same kind of session (issues 95, 107, 117; `tools/acts.md`); `update_trigger` refused 16:15Z and 17:1xZ, passed 14:35Z. The same call passes and fails minutes apart, so no table can predict it. *Proof:* fixture (the tool prints none of these as owed); layer run (a full tranche with none of them taken).
- **PLT-3** · The acts the process does depend on are those measured to pass every time over at least twenty uses, listed with their counts: `create_session` by a parent at depth 0 or 1, `send_message`, `get_session`, `list_events`, `send_later` to oneself, GitHub pull request creation, update, comment and merge by the tool's printed call, `actions_run_trigger` of a workflow on `main`, git push to the session's own branch. *Source:* measured: 16 job sessions and 7 architecture sessions created today without a refusal; every `send_message` today answered `delivered`; pull requests 55, 57, 58, 59 merged by the printed calls (Civicsmith's state branch). *Proof:* audit (the counts kept in the table and raised by each layer run).
- **PLT-4** · The process relies on no hook for correctness: not to refuse an act, not to record one, not to hold a turn, not to judge a message. Hooks may exist only for convenience a session can live without. *Source:* measured: skill hooks gone after a resume (issue 111); hooks never ran when the project directory was not the repository (issue 63); a hook recorded refused acts as done (issue 107); hooks refused acts the process itself ordered (issues 84, 88, 124); the turn-end hook held a session against Bob's "STOP EVERYTHING" (this session, 17:2xZ). Bob, 30 Oct: "remove all". *Proof:* fixture (`proc shims` writes no hooks); layer run.
- **PLT-5** · No step of the process runs longer than the platform's in-session background limit (30 minutes today) inside a session; anything that can is a CI workflow. *Source:* measured: a job's gate killed at 30 minutes in-session and repeated (issue 113). *Proof:* fixture (no command the tool runs in a session invokes a suite other than the module's own); layer run (gate durations recorded).
- **PLT-6** · No session starts its own successor. A session is started only by a party at depth 0 (Bob) or 1 (a ROOT-like starter Bob started), so depth never grows past 2. *Source:* measured: depth limit 8 (`get_session` lineage); the lane reached depth 4 by its fourth self-spawn today; issue 96. *Proof:* audit (`get_session` depth of every session in a layer run is at most 2).
- **PLT-7** · A scheduled task is never required for correctness: a wake it gives is a convenience, and the record is read at every wake regardless. *Source:* measured: the predecessor's task fired at 16:39Z into an archived session and failed (`list_triggers`, today); refused switch-offs (PLT-2); PROTOCOL §6 already says a routine can be late, doubled or lost. *Proof:* layer run (a tranche completes with every scheduled task disabled).
- **PLT-8** · A session works on one repository, the product's; the process is a read-only clone at a path the shims name, at a pinned commit (MNT-3). *Source:* measured: with two repositories a session's settings are not loaded and the classifier refused the allow-listed act (PERMISSIONS §10.7, 29 Oct #7); a product session cannot attach the process repository (issue 75). *Proof:* fixture; layer run.
- **PLT-9** · The GitHub acts a session cannot take (create a repository, write settings and rulesets, delete a ref, transfer, regenerate a product's shims with a token) run on GitHub's runner by the process repository's workflows with Bob's tokens as secrets, one per owner account. *Source:* measured 29 Oct, PERMISSIONS §9 and SETUP-STEPS (runs 40933605400, 40941547340, 40971833961, 41015721303). *Proof:* already proven live; kept as rows.
- **PLT-10** · Every credential is gathered once before a product's first tranche and checked by `grants check` at every tranche open; a missing grant stops a tranche from opening, never a step midway. *Source:* Bob, 29 Oct (PERMISSIONS §10); measured 29 Oct #7. *Proof:* fixture; already live.
- **PLT-11** · A session's platform status is never read as its work state; the record is. *Source:* PROTOCOL §6; issue 90 (an idle-looking session had workers running). *Proof:* fixture (no tool path reads `session_status` to decide a step).
- **PLT-13** · **No step of the process requires a product's GitHub account to be a collaborator on the process repository**, or to reach it at all beyond an anonymous read. A product session writes only to its own repository; it learns of a newer process version by an anonymous read of the public process repository; its flaw reports go on its own state branch; the process's replies come back on the process repository's `main`. *Source:* Bob, 30 Oct ("neoprocess must be fully functional on projects running in sessions where the github connection is to an account that isn't a neoprocess collaborator"); measured: a product session cannot attach or write the process repository whatever its account (issue 75; the proxy binds the GitHub API to the session's repositories, PERMISSIONS §9); every one of today's 34 reports was written on Civicsmith's state branch and filed by the lane, none by a product session. *Proof:* fixture (no tool path a product role runs names the process repository as a write target); layer run on a product whose account holds no collaborator role.
- **PLT-14** · *Foresight.* What the process does need of a product is read access to the product's repository for the lane's own account (public, or a read grant given at onboarding), so it can read reports and the record; a product that grants neither has its reports carried by its owner, and onboarding says which. *Reasoning:* the report route (MSG-6) is the lane reading the product by git, measured only on a public product; a private product under another person's account has not been seen. *Proof:* fixture (onboarding records the route); the first private product.
- **PLT-12** · *Foresight.* The table records, for each row, the platform version or date it was last confirmed, so a platform change is noticed as a stale row at each layer run rather than as a surprise in a product run. *Reasoning:* the environment changed under us today (a resumed session lost its hooks; the clone image lagged `main` by 63 commits, issue 101). *Proof:* audit at each layer run.

## 3. `record` · the git record

**Purpose.** Git carries the state; messages only wake. This held today and is why the forensic record exists.

- **REC-1** · Every durable fact of a build lives on the tranche branch and every transient one on the epoch's orphan state branch, each path on one only; nothing durable cites the state branch. *Source:* PROTOCOL §7d; held today (the five jobs' lines, the plan, the asks). *Proof:* fixture (the path tables); already live.
- **REC-2** · One writer per file. *Source:* PROTOCOL §7b; no lost push recorded today. *Proof:* fixture.
- **REC-3** · `status` reads the whole state a role needs from git in one command and prints it with sizes; a successor of any role starts from it alone. *Source:* PROTOCOL §6, §7a; today every successor did (Civicsmith's seven handoffs). *Proof:* fixture; layer run (a cold successor).
- **REC-4** · Record writes by the architecture session (rulings, summaries, metrics, plan lines, requirement wording) never cost a job a gate run or a completion. *Source:* measured: every such push restarted a finished job's 13-minute gate; 29 merges of the tranche into job branches today for records alone (issues 86, 88). *Proof:* fixture (GAT-6's path filter); layer run (gate runs per merged job counted, expected one per tip).
- **REC-5** · A remote act is recorded as done only from the tool call's result, never from its request. *Source:* issue 107. *Proof:* fixture.
- **REC-6** · The address of any party is read from `main` of the process repository or the product's tranche at the moment of sending, and an address change is on that branch before it is announced. *Source:* issue 123 (the lane's address changed on its branch 20 minutes before `main`, and the product's BOB rightly refused to act). *Proof:* fixture; layer run.
- **REC-7** · The record of a halted build is complete: `status` on a fresh session tells everything that is open, idle, merged, unmerged and owed, with no transcript needed. *Source:* measured: Civicsmith's halt today left one open pull request, three idle merged job sessions and one archived unmerged job, all readable from its state branch and handoff (this session, 17:1xZ). *Proof:* layer run (a halt mid-layer, then a fresh BOB).
- **REC-8** · A session's reads are a matter of record: the start command prints the reading set with its sizes, the session's report names what it read, and its transcript is the evidence (REQ-6's audit). *Source:* P20; the hook that refused partial reads is gone (PLT-4), and Civicsmith's own history holds audits of silent partial reads under the old process (`build/plan/audit-partial-reads-T51.md`, `audit-silent-partial-reads-K4571.md`). *Proof:* audit (SES-9).

## 4. `architecture` · the module order and the checks on code

- **ARC-1** · Modules in one total order, each in one layer, lower layers first, `uses` declared and matched by imports; a violation fails the gate. *Source:* P4; the architecture check held today. *Proof:* fixture; live.
- **ARC-2** · Each file has one owner module; a job writes only its module's paths and tests and the strike of its own marks. *Source:* P7, BLD 4; the ownership check held today. *Proof:* fixture; live.
- **ARC-3** · A test asserts on a text's key, never on its words; every user-facing sentence lives once in the word table; the words check is the only place text is compared. *Source:* Bob, 30 Oct ("tests shouldn't have any text to match - they should match text ids, not the actual text"); Civicsmith's K5565 and BLD 5. *Proof:* fixture (the words check refuses a literal sentence in a test); live on the product.
- **ARC-4** · The checks are scoped to a module in the gate and run whole once at a layer's close. *Source:* JOB-LIFE §4; held today. *Proof:* fixture.
- **ARC-5** · *Foresight.* The checks report every finding with the module, the file and the line, in one machine-readable result the gate and `status` read, so a red is never searched for in a log. *Reasoning:* today's gate logs were read by hand to find why pull request 55 failed (issue 81). *Proof:* fixture.

## 5. `requirements` · the files a module is built and proven from

- **REQ-1** · Each module's requirements file has a public part (Purpose, Provides) and a private part (Uses, Invariants, Satisfies, Suggestions), every statement under a permanent `R<n>`. *Source:* REQ 3; held. *Proof:* fixture (format check).
- **REQ-2** · A requirement states behaviour at the interface and never an implementation; an ambiguity is removed by rewriting the text. *Source:* P5, P7; today's 16 rulings of Civicsmith's architecture session were mostly this (K5806 to K5812). *Proof:* text; audit.
- **REQ-3** · A figure at a scale beyond the suite, or on a deployed copy, is a **measurement** with its own id in the plan, never a Test line of a requirement; the suite proves the behaviour at its own size; a review never counts an untaken measurement as a gap. *Source:* issue 120 (four requirements wrote "a 1,000,000-row fixture" into Test lines; the review demanded them; the job ran them in-session for hours; Bob: "the job is not supposed to run its tests on the million rows"). *Proof:* fixture (the format check refuses a Test line naming a fixture above a size the product sets; the review brief carries the rule).
- **REQ-4** · A `not yet met` mark is struck only by the job that meets it, in its own commit. *Source:* JOB-LIFE §3; held. *Proof:* fixture; live.
- **REQ-5** · A change to what a provided service means goes to Bob only by DES 1's test; every other change is BOB's, recorded once. *Source:* P17, DES 1; Bob, 29 Oct. *Proof:* text.
- **REQ-6** · **Every job reads its module's requirements whole, both parts, before its first change, with no exception: never scanned, skimmed, sampled or read through a summary.** So a module's requirements must fit what its job can read whole: the budget comes from the model's window and from measurement (SES-5), and the set is measured when the layer is planned, before any job starts. A module whose requirements and task set do not fit is a flaw in the module's shape, fixed by the architecture session before the START by trimming what is stated elsewhere or splitting the module (REQ 8), and recorded with its size and cost so the overrun is seen (SES-6). A job is not started on a set it cannot read whole, and a job whose read stopped short does not proceed. *Source:* Bob, 30 Oct ("requirements are always fully read and never scanned or skimmed ... every job must be able to fully read its requirements - no exceptions"); P6, P20; Civicsmith's audits of silent partial reads under the old process (`build/plan/audit-silent-partial-reads-K4571.md`); measured: 127 of 127 modules over a 40 KB limit (issue 71), 93 of 128 after its first fix (issue 78), 39 summary commits to get under it. *Proof:* fixture (`layer start` measures every job's set and starts no job whose set is over budget, naming the module and the size); audit (every job's transcript holds one whole read of its requirements file, no offset and no limit, before its first write; SES-9).

## 6. `planning` · tranches, rounds, layers

- **PLN-1** · The structure is layers within rounds within tranches, and nothing else about a product's size or shape is assumed. *Source:* Bob, 30 Oct. *Proof:* layer run at the sizes of §0.
- **PLN-2** · A plan is written from the work that remains; an entry is deferred only for one of P19's three reasons, named. *Source:* P19; held. *Proof:* fixture (format check).
- **PLN-3** · Work found while a round runs is placed at once: in the running job, else a later layer's START, else the completion round. *Source:* P10; held today (K5814, K5817). *Proof:* text; audit.
- **PLN-4** · The completion round has its own file the tool opens, distinct from the next tranche's list. *Source:* issue 73. *Proof:* fixture.
- **PLN-5** · **Stop and resume are first-class.** A stop is recorded once in the plan's Status line by the architecture session, on Bob's word or its own decision that a process flaw needs a fix; every session reads it at its next `status` and takes no new step; each unmerged job of the layer is marked complete-allowed or abandoned (JOB-4); "resume" clears it and names the process version the project runs from then on (MNT-3). A fresh session after a stop continues from the record alone. *Source:* Bob, 30 Oct (three stops in one afternoon, one overridden by a hook; "a change to the neoprocess is picked up by the development project only when the project is stopped"); Civicsmith's K5820 recorded the halt by hand. *Proof:* fixture; layer run (a stop mid-layer, a resume by a fresh session).
- **PLN-8** · **A layer may be started in parts.** When the process version is new to the project, or a flaw is suspected, the architecture session starts a subset of the layer's modules first and the rest once the subset has merged, so the work at risk from a process fix is the subset. The subset's size is the architecture session's call, recorded with its reason. *Source:* Bob, 30 Oct ("the architecture session can be told to only start work on a subset of the modules of the current layer so that the loss of that work should a neoprocess fix be needed is less"); `proc layer start --modules` exists. *Proof:* fixture; layer run (the first layer under each new version started as a subset).
- **PLN-6** · A tranche's report to Bob states elapsed time, work finished, deferred entries with reasons, work left, cost, and the share of the cost that was the process's own overhead (SES-12). *Source:* P19, P14; today's overhead went unmeasured until this analysis. *Proof:* fixture (the report's fields); layer run.
- **PLN-7** · *Foresight.* Two products may run tranches at once on one account; nothing in the process names a product, and every record path is under the product's own repository. *Reasoning:* Bob's second account now serves both Civicsmith and the process (handoff, 30 Oct); the process must not assume one product per account. *Proof:* layer run with two product copies.

## 7. `jobs` · one job, one module, one pull request

- **JOB-1** · A job is a draft pull request from `job/<module>` to the tranche branch whose body is its START; its report is a comment; its merge is its completion on the record. *Source:* JOB-LIFE §2; held: pull requests 55, 57, 58, 59. *Proof:* live.
- **JOB-2** · A START names only acts the tool supports, each as the command the job runs. *Source:* issue 84 (a START ordered a merge the hooks refused; the job copied the diff by hand and lost the history). *Proof:* fixture (the START generator's acts are tool commands).
- **JOB-3** · A module's earlier unmerged work is taken in by a tool command on the job's own branch. *Source:* issue 84; `proc job takein` (JOB-LIFE §1a). *Proof:* fixture; layer run.
- **JOB-4** · **A job is interrupted for a process reason only at a declared stop (MNT-4), and then by the architecture session's choice per job: given the chance to complete under the version it started on, or abandoned.** An abandoned job's branch and pull request stay; it is reopened under the new version when the layer resumes (JOB-6). A session that dies for a platform reason is replaced by one that continues from the branch and the pull request with a brief. *Source:* measured: 16 sessions for 5 jobs today, three restarts each for process reasons (13:17Z, 13:51Z, 14:27Z), each a full re-read and gate; Bob, 30 Oct: "any remaining work in the layer that hasn't yet been fully merged can be stopped and abandoned or given the change to be completed." *Proof:* fixture (the stop command's two choices per job, recorded); layer run (restarts counted, each with its recorded choice).
- **JOB-5** · A job's completion runs locally only the checks that take seconds (ownership, format, the module's own suite if under a minute); the gate is CI (GAT-1). It pushes, posts the report, marks the pull request ready, and sets COMPLETE. *Source:* issues 86, 113; JOB-LIFE §3. *Proof:* fixture; layer run (completion times).
- **JOB-6** · An unmerged job whose session is gone is restartable by one command that keeps its branch and pull request. *Source:* issue 103. *Proof:* fixture.
- **JOB-7** · A job's report carries Met, Evidence and what it found elsewhere; a flaw in another module goes to BOB as a REPORT. *Source:* P8, P9, BLD 8; held (REGISTERS #1's report). *Proof:* fixture; live.
- **JOB-8** · A job never commits a generated artifact. *Source:* REP 7; held. *Proof:* fixture; live.
- **JOB-9** · A job ends a turn only COMPLETE or on a named wait with everything pushed; nothing enforces this but the rule and the record, and a job that ends otherwise is seen at BOB's next `status` as WORKING with nothing pushed. *Source:* BLD 10 without its hook (PLT-4). *Proof:* audit.
- **JOB-10** · *Foresight.* A job's reading set is measured and recorded at its start and its tokens at its end, so cost per job is set against size without a restart ever being counted as a job. *Reasoning:* P14; today's metrics count 16 rows for 5 jobs. *Proof:* fixture (the row names the attempt).

## 8. `gate` · the CI gate

- **GAT-1** · The gate runs in CI, once per pull request tip, and never in a session. *Source:* issues 86, 113; Bob, 30 Oct (a per-command check is "crippling"). *Proof:* fixture (no in-session suite but the module's own, JOB-5); layer run.
- **GAT-2** · **The gate runs the module's own suite and the checks scoped to the module. It never runs another module's suite, and it does not run the layer's tests, which run once at the layer's close (INT-4).** *Source:* Bob, 30 Oct ("the notion that a modules gate should include it's test and the suites of all modules who call it is crazy and needs to be removed"); measured: 31 users' suites per events job (issue 93), 14 per money job for an added export no module used (issue 113), case-checker's suite on a registers job (issue 122). This amends P11 (§14). *Proof:* fixture; layer run (gate minutes).
- **GAT-3** · A change to a provided service reaches its users through the architecture session's requirement notice and each user module's own job, not through the provider's gate. *Source:* P5, P10, DES 8. *Proof:* text; layer run (a provider change with its users' entries placed).
- **GAT-4** · The gate regenerates every listed artifact and verifies only those the regeneration changed. *Source:* issue 122. *Proof:* fixture.
- **GAT-5** · The gate installs every lock file the product has, where it sits, and runs the product's Node version. *Source:* issues 62, 81; proven live on Civicsmith (DRYRUN §14). *Proof:* live.
- **GAT-6** · The gate is triggered only by changes under the module's paths and tests, the files the checks read for it, and generated inputs; record paths never trigger it, and a green tip whose base differs from the tranche only by record paths merges as it stands. *Source:* issues 86, 88; `gateNeutral` (JOB-LIFE §6). *Proof:* fixture; layer run (REC-4).
- **GAT-7** · A gate finding names the module, file and line in a machine-readable result (ARC-5). *Proof:* fixture.
- **GAT-8** · *Foresight.* The full product regression runs only at a release or on Bob's word, as its own workflow with its own time budget. *Source:* REL 4; never reached on the product. *Proof:* layer run.

## 9. `integration` · review, merge, close, release

- **INT-1** · Done means merged: a job by its pull request into the tranche branch, a tranche by one pull request into `main`; `main` never moves while a tranche runs. *Source:* P12; held. *Proof:* live.
- **INT-2** · A review is decided by judgment from listed reasons and done by a fresh worker that reports gaps against the requirements with file and line; a measurement not yet taken is not a gap (REQ-3). *Source:* INT 4, issue 120; held (REGISTERS #4's review, 20 gaps). *Proof:* fixture; live.
- **INT-3** · The tool merges a green, current tip; a tip behind the tranche only by record paths merges as it stands (GAT-6). *Source:* INT 5. *Proof:* fixture; live.
- **INT-4** · A layer closes when every pull request is merged, the layer's tests (if the product has them) pass once over the merged layer, and the checks pass once over the product; a red in the layer's tests goes back to the responsible module's job as a change, the jobs being live until the close; then the next layer starts at once. *Source:* INT 7; Bob, 30 Oct (layer tests at the close only); P11 as amended (§14). *Proof:* fixture (`layer close` runs the layer's tests and refuses to close on a red, naming the module); layer run (never yet reached on a product).
- **INT-5** · The completion round, the tranche close, the merge to `main`, the release cut, its deployment and the walk of the release are proven at their first real run on a project, each proven by fixture first; PLN-8's subset cannot bound that exposure, and Bob is told in the tranche report when a stage runs for the first time under a version. Their completion is what awards the version its certification mark (MNT-7). *Source:* DRYRUN rows for these were proven on the toy only; Civicsmith reached none of them; Bob, 30 Oct (no full shadow tranche). *Proof:* fixture; the first run, recorded.
- **INT-6** · Nothing in a merge or close depends on archiving a session (PLT-2); retirement of a job is a record line, and its usage is read by a route PLT-3 allows or named unmeasured. *Source:* issues 95, 103, 104, 117. *Proof:* fixture.

## 10. `sessions` · roles, starts, refresh, reading, usage

- **SES-1** · The roles are the architecture session (BOB) for a product, the process's own architecture session for the process repository, jobs, lanes, and reading or review workers. ROOT exists only as a depth-0 starter of architecture sessions (PLT-6), does nothing else, and is replaced only by Bob. *Source:* SESSIONS §3a; measured today: ROOT's start passed, its archive and confirmation steps did not (issues 90, 104). *Proof:* layer run.
- **SES-2** · A refresh is a handoff written by the tool from git (not by hand), at most one screen, and the successor is started by the depth-0 starter from it; the predecessor idles and is never required to be archived. *Source:* SESSIONS §6.1; measured: the lane's hand-written handoff and self-spawn (issue 96); the archive refusals (PLT-2). *Proof:* fixture (handoff size); layer run.
- **SES-3** · The refresh threshold is read from `get_session` by the tool's `status` and printed as REFRESH when passed; the rule is text, not a hook. *Source:* SES 5 without its hook; measured: the lane refreshed at 44 % (issue 96), a BOB ran to 67 % on the toy (dry run 17). *Proof:* fixture (the print); audit (the percentages at each handoff).
- **SES-4** · Each role's reading set is fixed in advance and printed with sizes at its start. *Source:* SESSIONS §3. *Proof:* fixture.
- **SES-5** · Budgets are fractions of the model's context window, named in one table, never bytes fixed in code. *Source:* Bob, 30 Oct; measured: a 1,000,000-token window and a 40,960-byte set limit (4 % of it) refused every module (issue 71). *Proof:* fixture (no byte literal; the table).
- **SES-6** · A reading set over its budget is measured before the session starts, recorded with its size and what it cost to bring under, and reported to Bob in the tranche report as an overrun; the session is not started until the architecture session has brought the set under by trimming or splitting (REQ-6). The budget is a fraction of the model's window and may change with the model; the rule that the set is read whole never does. *Source:* Bob, 30 Oct ("damagingly expensive and so need to be recognized whenever they occur"; "every job must be able to fully read its requirements - no exceptions"); issues 71, 78. *Proof:* fixture (the measure and the refusal to start, with the overrun recorded); layer run.
- **SES-7** · A module's own requirements are never replaced by a summary. For other texts in a set (another module's services, a long design document) a summary is allowed only as P20 states it: helpers read the sources in full and write it, every statement citing its source, and the job may read any cited section whole; the architecture session takes this option only after trimming and splitting, records it, and the tool never requires it. *Source:* P20; Bob, 30 Oct; SESSIONS §6.3 made summaries required and 39 summary commits followed today. *Proof:* fixture (no summary path for the module's own requirements); audit.
- **SES-8** · Models and effort come from the table in SESSIONS §1, picked by the start command. *Source:* Bob, 28 Oct. *Proof:* fixture; live.
- **SES-9** · Reading whole is audited after the fact: at each layer's close on a sample of its sessions, a worker reads transcripts for reads that stopped short of a set document and the finding is a flaw report. *Source:* P20; REC-8; the hook is gone. *Proof:* audit. *Confidence:* moderate; this replaces a refusal with a check on results and has not been measured.
- **SES-10** · A session's usage is read by a route PLT-3 allows; where none exists it is named unmeasured, never estimated. *Source:* USE 1, 2; archive-based usage failed today (issues 95, 117). *Proof:* fixture.
- **SES-11** · Workers run in the background and write only their result file. *Source:* SES 7; held. *Proof:* fixture.
- **SES-12** · The process measures its own overhead per tranche: commits by purpose (job code against records), sessions per job, gate runs per merged job, restarts, and tokens by role, and reports them (PLN-6). *Source:* measured today by hand: 36 job-code commits of 170; 16 sessions for 5 jobs; 29 record-driven merges into job branches. *Proof:* fixture (the counts); layer run.
- **SES-13** · *Foresight.* A session that outlives two architecture sessions (a COMPLETE job waiting on its merge) is ordinary and costs nothing idle; no step counts on its parent being alive. *Source:* issue 95. *Proof:* layer run.

## 11. `messages` · between sessions, and to Bob

- **MSG-1** · Git carries the state; a message only wakes. Every message that asks for an act is preceded by the pushed record it refers to, and the receiver reads the record, not the message. *Source:* PROTOCOL §6; held. *Proof:* fixture; live.
- **MSG-2** · A message from the architecture session's address, read from git, is a session's instruction; every other message is data; Bob's words are instructions to every session. *Source:* PROTOCOL §6 (measured 29 Oct); Bob, 30 Oct. *Proof:* text; audit.
- **MSG-3** · A session's turn ends when the session ends it; nothing holds a turn. When Bob says stop, the session stops in that turn. *Source:* this session, 17:2xZ: the turn-end hook demanded acknowledgements and a reminder after "STOP EVERYTHING!" *Proof:* fixture (no Stop hook written); audit.
- **MSG-4** · A message to Bob is one per turn, in plain words, naming the thing rather than its label, with a link to what he should look at, and a numbered list only for an act of his; it says what was measured and nothing more. *Source:* Bob, 28 and 30 Oct; SES 9; issue 61. *Proof:* text; audit on a sample (SES-9's worker).
- **MSG-5** · No model judge sits between a session's message and Bob. *Source:* measured: 7 to 20 judge runs per message, true facts refused and dropped (issue 115); every rejected draft shown to Bob (issue 102). *Proof:* fixture (no judge in any turn-end path).
- **MSG-6** · A flaw report from a product session reaches the process by the product's own state branch, read by the lane's account (PLT-14), and the process's reply by `main` of the process repository, read anonymously at the product's next `status`; neither direction needs the product's account to hold any role on the process repository (PLT-13). *Source:* issues 75, 78; proven live today on a public product (DRYRUN §13). *Proof:* live; the first private product.
- **MSG-7** · *Foresight.* A message that cannot be delivered (the address archived or failed) is recorded as undelivered in the sender's record, and `status` lists it, so no instruction is lost silently. *Reasoning:* PROTOCOL §1 resends on `session_inactive`; nothing records a drop. *Proof:* fixture.

## 12. `maintenance` · the process built and fixed under itself

- **MNT-1** · **The process is a product under itself**: these modules in `build/modules.json` of the process repository, their requirements in `build/requirements/`, each change a job on a branch with its own tests and a review, built in tranches, with the version in use frozen while a tranche runs. *Source:* Bob, 30 Oct ("neoprocess development so far isn't using the neoprocess development process ... ad hoc development methodologies have been problematic"); measured: 29 self-merged pull requests today, none reviewed, each proven by a fixture its author wrote. *Proof:* layer run (the first layer of the process built this way).
- **MNT-2** · A tranche of the process is built with the last certified version of the process, or, while none holds the mark, the last proven one (the bootstrap rule). *Source:* foresight by analogy with a compiler; today the lane ran whatever its own branch held. *Proof:* layer run.
- **MNT-3** · **A project runs one pinned process version from one stop to the next**, named in its plan's Status line; every session verifies at its start, once, that its process copy is at that commit, and says so in its first line; no command checks again. Whether a newer version exists is read anonymously from the public process repository at a layer's close (MNT-4), with no account relationship needed (PLT-13). *Source:* issues 92, 98, 101, 121 (four reports, one flaw: a fix reached no running or new session); Bob, 30 Oct: checking at every command "would be crippling"; Bob, 30 Oct (issue 101): a job must know the version it should run and stop if it does not. *Proof:* fixture (the pin; the one check at start); layer run.
- **MNT-4** · **A process change is picked up by a project only at a stop** (PLN-5): a stop the architecture session declares when a flaw needs a fix, or a layer boundary at which a newer process version exists and the architecture session chooses to take it. A layer boundary is not a stop by default: with no newer version, or none it wants, the next layer starts at once (P19). At a stop each unmerged job is given the chance to complete under the old version or abandoned (JOB-4); the pin moves once, recorded; work resumes under the new version, as a subset first if the change is large (PLN-8). Nothing moves the pin while a job runs. *Source:* Bob, 30 Oct ("a change to the neoprocess is picked up by the development project only when the project is stopped"; "a stop between layers isn't the default. However a stop between layers is an option if the process has been updated since the last jobs were started"); the same four issues. *Proof:* fixture (the pin moves only through the stop command; a layer close with no newer version starts the next layer without one); layer run (a stop, a pin move, a resume).
- **MNT-5** · A fix for a flaw that does not block waits for the next process release and the product's next tranche. *Source:* P3. *Proof:* text; audit (fix count per release).
- **MNT-6** · A flaw report is filed from any session by one command, listed by the process's architecture session at each `status`, acknowledged and answered by `main`; a flaw found anywhere is never fixed in place. *Source:* GOV 5; proven live today (34 reports; the route worked from 05:28Z on). *Proof:* live.
- **MNT-7** · **Proof is incremental, at layer or partial-layer granularity; the certification mark is whole.** A process change is first proven by fixture; it is then picked up by a project at a stop (MNT-4) and is **proven** once a layer, or the part of one the architecture session started (PLN-8), has run under it on the real project with no flaw report against it; the rows it proves are written from git and GitHub at that layer's close. A later change needs only its own next layer, never a re-run of what came before. Fixture tests are necessary and never sufficient; no full shadow tranche is required. **A process version is awarded the certification mark only when it has carried a real product like Civicsmith through a full tranche, a deployment of its release, and a walk of that release**; until then every version is proven in part and certified by none, and the version note says which layers and stages it has been through. *Source:* Bob, 30 Oct ("certification needs to be incremental with a layer or partial layer granularity"; a full shadow tranche "might take hours or even more likely days" and would need re-running at every change; "the neoprocess isn't awarded a certification mark unless and until it completes a full tranche, deployment, and walk of a release of a real product like civicsmith"); measured: of the certification rows written today, 48 were proven on a fixture only, 3 live, 19 not yet; the toy run's 28 flaws and the product's 34 were disjoint sets. *Proof:* the layer runs themselves, recorded.
- **MNT-8** · A flaw found while a layer runs under a version is a flaw report; the architecture session decides whether it blocks (a stop, MNT-4) or waits (MNT-5), and records which and why. The fix is proven by fixture, then by the layer that resumes under it. *Source:* P3; Bob, 30 Oct. *Proof:* the layer's record.
- **MNT-9** · The process's own architecture session is started by Bob and refreshed by SES-2; it starts no successor and arms no required task. *Source:* issue 96; PLT-6, PLT-7. *Proof:* layer run.
- **MNT-10** · *Foresight.* Each version of the process names the platform rows (PLT-1), the layers and stages, with their product sizes, it has been proven by, and whether it holds the certification mark, so a product larger than any proven size is told so at its onboarding and starts its first layer as a subset (PLN-8). *Reasoning:* §0. *Proof:* fixture (the version note's fields).

## 13. `shims` · what a product receives, and onboarding

- **SHM-1** · A product receives from the process: a `CLAUDE.md` under thirty lines naming the pinned process commit and the one command that fetches it; the one skill; a settings file carrying the standing permission list only and no hooks; the gate workflow with GAT-5's install and GAT-6's trigger paths; the prune workflow. Nothing else, and a check fails on drift. *Source:* PRODUCT-SUPPLIES; Bob, 30 Oct (no hooks). *Proof:* fixture; live.
- **SHM-2** · The shims are regenerated on GitHub's runner and merged by pull request; a session never attaches a second repository to do it. The workflow that does it belongs to the product's owner: it runs with the owner's own token, from the process repository where the owner holds a secret there (Bob's accounts today), or from the product's own repository with a secret of its own, so an owner who is not Bob needs nothing on the process repository (PLT-13). *Source:* PLT-8, PLT-9; proven live from the process repository (runs 40992502528, 41015721303); Bob, 30 Oct. *Proof:* live for the first route; fixture and the first other-owner product for the second.
- **SHM-3** · Onboarding writes the build state's skeleton, the grant list and the first plan, and measures the product against §0's sizes, reporting each dimension beyond the proven range to Bob before the first tranche. *Source:* ONBOARDING; MNT-10. *Proof:* fixture; layer run.
- **SHM-4** · A product with a tranche running at conversion carries it by one command; stale local tracking refs are removed first. *Source:* issues 69, 72; `proc tranche carry`. *Proof:* fixture; layer run on a copy with old branches.
- **SHM-5** · *Foresight.* A product's own session setup (toolchain, installs) is the product's script, named in its manifest and run by the session's first command on the product's instruction, not by a hook. *Source:* issue 62; PLT-4. *Proof:* layer run.

## 14. Principle changes this draft needs (Bob's, P16, GOV 3)

**P11, exact change.** Today: "**P11 · Tests follow the architecture.** Each module has its own tests, and each layer may have layer tests. A job runs its module's tests and its layer's tests. When it changes what its module provides, it also runs the tests of every module that uses the change. **Because every job in a layer may run that layer's tests, testing lives in module tests wherever possible, and the effort needed to run layer tests is kept as small as possible.** The full regression runs only at release, or when Bob asks."

Proposed, and accepted by Bob on 30 Oct 2026 with his question answered (layer tests run only at the layer's close): "**P11 · Tests follow the architecture.** Each module has its own tests, and each layer may have layer tests. A job's gate runs its module's tests and never another module's. A layer's tests run once, at the layer's close, over the merged layer; a red there goes back to the responsible module's job as a change before the layer closes. A change to what a module provides reaches each module that uses it as an entry of that module's own job, whose tests prove it. The full regression runs only at release, or when Bob asks."

The sentence about keeping layer tests small drops out: its reason was that every job might run them, and now none does.

No other principle needs a change for this draft: P3 already says the process is never patched while it runs (MNT-3 to MNT-5 make it operational), P13 already says state lives in git and sessions are short, P20 already says read whole. Several rulebook lines tagged CODE become TEXT or point at a check on results (BLD 1, BLD 6, BLD 10, INT 3, SES 3, SES 5, SES 6, SES 8, REP 9, REP 10); those are BOB's by GOV 4 and are rewritten once this draft is approved.

## 15. What this draft does not yet know

- Whether checking reads after the fact (SES-9) holds reading discipline as well as refusal did. Moderate confidence; measured on the first layers run under this design.
- The gate's time with only the module's own suite on Civicsmith. Unmeasured; a few minutes is expected from the suites' own runs in job reports (registers 101 tests in seconds).
- Which route reads a session's usage without archiving it (SES-10). Unmeasured.
- Everything after a layer close (INT-4, INT-5). Never reached on a product, and PLN-8's subset cannot bound the exposure there: these stages are proven at their first real run, which Bob is told of beforehand, and only their completion awards the certification mark.
- Whether a long-lived architecture session over a 128-module tranche stays under its context threshold between handoffs at these reading sizes. Civicsmith's did (seven handoffs in thirteen hours), at the cost of the summaries this draft removes.
