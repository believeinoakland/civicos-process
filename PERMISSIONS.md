# Permissions: how neoProcess handles a refused act

**Status** · In force from 2026-10-29, certified on the dry run N1 (`dryrun/N1/CERTIFICATION.md`; the run and its flaws, `lane-neoprocess/DRYRUN.md`). Drafted, neoProcess #4, 2026-10-29, on Bob's direction of the same day: "the neoProcess also needs to robustly handle permissions, something the current process continually struggles with." What is Bob's here is named in §6.

## 1. What refuses an act, measured

Four different things refuse a session's act, and they behave differently. Each was met on 29 Oct (neoProcess #3 and #4), with the evidence named:

| what refuses | how it decides | cleared by | measured |
| --- | --- | --- | --- |
| **The process's own hooks** (`tools/hooks.mjs`) | the rule it names, in code; the refusal names the route that does the act | taking that route | the fixture tests (`tools/test/hooks.test.mjs`) |
| **The auto-mode safety classifier** | a judgment of the command's text or the tool call, by category (`Irreversible Local Destruction`, `Interfere With Workloads`, …); it reads the act, not the state | nothing in a settings file: `.claude/settings.json` here already allows `archive_session`, and the classifier still refused #4's archive of #3 ("Interfere With Workloads"); Bob can allow the act in the refused session | #4: `git reset --hard origin/<branch>` refused on a clean checkout, while `git merge --ff-only origin/<branch>`, the same result, passed; #4's `archive_session` of its own child (PROBE-J12 #1) passed and of its parent (#3) was refused; #3's archives of #2 and of itself were refused |
| **The platform's scope** | what the account's GitHub app, the git proxy and the session's repository list allow; an error, not a prompt | Bob, in a settings page (the app's repositories, the environment's hosts) | #4: `create_repository` in the organization answered 404; REP 2: the git proxy refuses hand deletes and tags |
| **The environment's own Stop hook** (`~/.claude/stop-hook-git-check.sh`) | a turn may not end with uncommitted or untracked files | committing, or holding until the hook gives up | PROBE-G, PROBE-J12: a session told not to commit held, at the cost of a loop |

The old process's struggle (`HISTORY.md`; K1702, K4696, K5120, K5293) is that every refusal is met **during** a step, by the session that cannot clear it, and is then relayed to Bob one at a time: the standing list grew by incident, a settings rule never cleared the classifier, and an approval typed in one session never reached the next.

## 2. The design: no product session meets an unpredicted refusal

Derived from P3 (correct before used), P16 (what must hold every time is code) and P17 (the act only Bob can take is named and walked through):

1. **An act table, proven on the dry run.** `tools/acts.md` lists every act the process takes, per role: the tool or command, the route the tool uses, the relation it needs (its own branch; a session it created; a pull request `proc` printed), and the result measured on the toy. The dry run tries every row in its role (certification rows X1–X5). A product session takes no act the table has not seen pass. An act that is refused in a product run and is not in the table is a process flaw: it stops the work until the table and the route are fixed (P3), never a workaround.
2. **Routes the checks accept by construction.** The tool never uses a destructive verb where a constructive one gives the same result: `merge --ff-only` or `checkout -B` for a stale branch, never `reset --hard`; no force, no rewrite; the one remote delete (a closed epoch's state branch, PROTOCOL §7d) is in the table as a row the proxy must be seen to allow, else the branch is left for Bob's prune workflow (REP 4) and the design says so.
3. **Routed by relation.** The classifier lets a session act on what it created and refuses what it did not: a session archives only its own children, so ROOT archives every BOB, BOB archives every job and lane, and a successor of any role is started by that role's parent, never by its predecessor (R10; PROTOCOL §7a). The neoProcess lane itself, whose sessions start each other, is the counter-example: #2 and #3 can be archived only by Bob.
4. **One standing list, applied by the tool.** The acts Bob allows without asking are one file in the process repository (`permissions.json`, Bob's policy), from which `proc shims` writes each product's `.claude/settings.json`; the gate fails on drift. It covers the permission prompt only; it never clears the classifier (§1), and it never holds an act that loosens a standing safety rule (REP 2). Whether a session may write that file at seeding is itself a table row (X4; K1702 says a session's edit of settings was refused): if refused, Bob commits it once and the tool only checks drift.
5. **A refusal is a recorded, routed, counted event.** A refused session runs `proc refused --act "<the one act>" --kind <hook|classifier|scope|platform> --reason "<the refusal's words>"`: one line on the state branch, listed by `proc status` as `REFUSED <role> <act>`. BOB routes it from the table: to the party whose relation passes (the parent archives), to the route the tool offers, or, when only Bob can clear it, `NEEDS BOB` with one line naming the session and the act. Every refusal is a metrics row (kind, role, act), so a tranche's report states how many refusals it met and how many the table had not predicted; the number to reach is zero unpredicted.
6. **A self-check at every start.** `proc takeover`, `job start` and `lane start` dry-fire the role's reaching acts (`git push --dry-run` to its own branch; a fetch of the branches it reads; the state branch written), so a scope or proxy problem shows in the first turn, before any work depends on it.

## 3. What the hooks already do

The process's hooks are the first line: they refuse, with the route named, everything that must never happen (REP 2, 3, 5; SES 1, 6, 8; INT 3, 9; a job's acts on its PR), so a session rarely reaches the classifier with an act it should not take. What then reaches the classifier is, by construction, an act the table says passes, or an unpredicted refusal (§2.1). Three Stop refusals running, whatever their text, let the turn end, so a cause the session cannot clear never loops.

- **X5, X7 (a standing-list rule, and the hook's `allow`, clearing a prompt)**: provable only in a product run with a session in Accept edits; every session of N1 ran in Auto, where no prompt is shown. Seen all the same: the deny rule `Bash(git rebase *)` refused BOB #2's rebase in Auto, so the list is read and applied in a cloud session.

## 5. Rules, as they will read

Rulebook REP 9 and 10 and GOV 9 are rewritten from §2 and §8 (BOB's, the mechanism; written 29 Oct by #6, `rulebooks/repository.md` and `governance.md`); their substance: *A refused act is recorded by `proc refused` and routed from the act table, never worked around; an unpredicted refusal in a product run stops the work until the table and the route are fixed (P3, P16, P17).* *The standing list is one file in the process repository, Bob's; the tool writes each product's settings from it and fails on drift (P16, P17).* *A session archives only sessions it created; a role's successor is started by the role's parent (P13; PROTOCOL §7a).*

## 6. Bob's standing approval (29 Oct 2026, his words, on record)

> "The neoProcess will be involved initially in development. Development product will be controlled using git. So nothing can be lost, and data used during development is throwaway. The only secrets are those stored in environment variables or other password managers away from CC. So releases, test IDs, and all other elements that would be more closely guarded in a customer's workflow are all 100% just for testing. So there needs to be an understanding about all of this up front. I need to be able to go on record as approving CC to do whatever it needs to do related to development, testing, and walker deployments without my having to provide any further approvals. I know that there's a way of giving this ongoing approval and for that approval to be properly partitioned and managed so that subsequent sessions and lanes can do what they need without asking for more permissions."

This is the ruling the standing list derives from (P17: policy; GOV 8: his words govern, BOB's details marked). BOB's details (P17):

- **What the approval clears, and how it is carried.** The platform (its documentation, read 29 Oct) sets a cloud session's permission mode at its creation, by the surface that starts it; a settings file cannot raise it, and a child session is never more permissive than its parent (`create_session`). So the approval is carried in two places the process controls, not in a mode: (1) **the standing list**, `permissions.json` in the process repository, from which `proc shims` writes each product's `.claude/settings.json` `permissions.allow` rules (every act of the act table that a permission prompt would otherwise stop: the tool's commands, the tests, pushes to the session's own branches, the session tools, the pull-request tools), so every session on the product, now and later, holds the same approval without asking; (2) **the act table and its routes** (§2.1–§2.3), so that what the process asks of a session is an act the checks accept.
- **What it does not clear, measured.** The auto-mode safety classifier judges each act by category and is not read from a settings file: the allow rule for `archive_session` in this repository's settings did not stop the classifier refusing #4's archive of its parent. The process therefore does not rely on approval for those acts: it removes them (no hard reset, no force, no rewrite) or routes them to the party whose relation the classifier accepts (a parent archives). A refusal that still occurs is an unpredicted one (§2.5), a process flaw to fix in the table, never a question to Bob.
- **The partition.** The list is one file, Bob's, in the process repository; a product repository holds only the copy the tool writes and the gate checks for drift; nothing in it loosens a standing safety rule (REP 2), and nothing in it touches a secret, which stays in environment variables and password managers away from the sessions, as Bob says.

## 8. Best practice, from Claude Code's documentation (read 29 Oct 2026; Bob: best of breed, for every project under neoProcess)

Read by a worker from code.claude.com/docs (permissions, settings, permission-modes, hooks, managed-settings, claude-code-on-the-web, cloud-environments, headless, the Agent SDK's permissions); each fact names its page. The model this yields, layer by layer, and what it changes above:

1. **Rules are enforced by Claude Code, never by the model** (permissions): "Instructions in your prompt or CLAUDE.md don't change what Claude Code allows." So the process's standing texts never carry a permission; the files and hooks below do.
2. **Precedence is deny, then ask, then allow; the first match wins, and an allow never carves an exception out of a deny** (permissions). Best practice is therefore a short **deny list of the standing safety rules** beside the allow list: force push, `git reset --hard`, `git clean -fd`, `git stash drop`, a push to `main`, a remote delete by hand. `permissions.json` now carries `deny` as well as `allow`, and `proc shims` writes both. The documentation itself says Bash rules "aren't a security boundary" (`git -C . push` escapes `Bash(git push *)`): the hooks remain the first line (§3), the rules the second.
3. **A cloud session reads the repository's `.claude/settings.json`** (settings, "Settings in cloud sessions"): its permission rules, hooks and env, in a single-repository session; never the user's or the local file. So the list the tool writes at seeding is the right home for a project's standing approval, and it travels with the clone. In a project's cloud threads, none of it applies (not documented how a thread session is then approved): the process starts its sessions by `create_session` on the repository, never in a project thread.
4. **The mode is set by the surface that starts the session** (permission-modes; this platform's own documentation): cloud offers Accept edits, Plan and Auto; Bypass is not available and `defaultMode: bypassPermissions` or `dontAsk` in a settings file is silently ignored; a child is never more permissive than its parent (`create_session`). So the approval is never a mode. In **Accept edits** a prompt would stop a Bash or MCP call the list does not allow: the list covers them. In **Auto**, allow, ask and deny rules "resolve immediately", except protected-path writes and critical-path removals, and broad allow rules are dropped on entry (`Bash(*)`, wildcarded interpreters such as `Bash(python*)`, `Agent`): the list therefore names the tool's commands narrowly, and the acts the classifier blocks by default (force push, `reset --hard`, production deploys, merging around CI) are ones the process never takes (§2.2). **Auto mode pauses after 3 consecutive or 20 total blocks**: an unpredicted refusal is not only a flaw but, repeated, stops the session, which is the strongest reason for §2.1's zero.
5. **A refused act is approved only in its own session, by naming the act and its specifics** (permission-modes: "naming the verb alone clears nothing"; `/permissions`, the Recently denied tab). This is the old process's struggle in the platform's own words (§1), and why the process avoids reaching it (§2) and records what it cannot avoid (§2.5). Routine patterns go to `autoMode.allow` (permission-modes); whether a settings file carries that key for a cloud session is row X6.
6. **A PreToolUse hook may answer `allow`, which skips the prompt** (hooks: "permissionDecision"), though never past a matching deny or ask rule, a critical-path removal or a network-path read. So the process's hook, which already knows the role and the act, can pre-approve the acts of the act table for that role, and the settings list shrinks to the MCP tools and the deny rules. Built as `allowReason` in `tools/hooks.mjs` (#5, 29 Oct), asked only once no refusal applies: a Bash command is answered `allow` only when every part of it is one of the tool's own commands (`node <process>/tools/proc.mjs …`), the checks (`checks/run.mjs`), the tests (`node --test …`), a read of git (status, log, diff, show, fetch, a listing of branches and remotes …), a push to the role's own branch, a `cd`, or a read-only filter (`head`, `tail`, `grep`, `wc`); a substitution, a redirect to a file, a background `&`, `--output` or any other part makes the whole command fall through to the rules and the mode. Fixture test: `tools/test/hooks.test.mjs`. The settings list keeps those acts until row X7 shows a hook's `allow` clears a prompt in a cloud session; only then does it shrink to the MCP tools and the deny rules.
7. **Managed settings reach cloud sessions when they are server-managed** (settings; managed-settings: "a managed-settings.json file or MDM profile on your device doesn't reach a cloud session. Your organization's server-managed settings do"), and nothing in a repository overrides a managed key. The best-of-breed partition for every project is therefore: the deny list and the standing allow list set **once, server-managed, in the claude.ai admin console** by Bob (his, an act on his organization: §7), applying to every cloud session of every product, with `allowManagedPermissionRulesOnly` optional; the repository file the tool writes is the same list, kept for sessions the console does not cover and for drift. Until Bob sets it, the repository file alone carries the approval.
8. **Secrets stay outside the session** (cloud-environments): a network secret is injected by the agent proxy after a request leaves the VM and "doesn't appear in the session's environment variables or in any file"; environment variables are readable by anyone who uses the environment. This is Bob's rule of §6 as the platform provides it: a product's keys are network secrets on an organization-shared environment with Custom network access, never variables, never files, and the act table never carries a secret.
9. **Nothing is lost in development** (Bob, §6; cloud-environments: "a fresh clone of your repository"): the sessions' clones are throwaway, the record is git, so the deny list protects history (REP 2) and nothing else needs guarding; what a customer's workflow would guard (releases, test ids) is testing here, and the list says so.
10. **Measured where the documentation is silent**: a child session's mode (never above its parent: this platform's `create_session`), the trust dialog for a repository's allow rules in a cloud session (X4), `autoMode.allow` (X6), a hook's `allow` (X7), server-managed rules reaching a product's sessions (X8, once Bob sets them).

## 9. The process's own tokens (Bob, 29 Oct 2026, 16:00Z)

Bob's requirement, in his words: *"I'm talking about a development process having tokens with sufficient access that it can take care of creating and configuring development-only repos without my involvement. I'm talking about the development process having a Cloudflare token with sufficient access that it can make development-related changes to the Cloudflare account."* Policy, his (P17): the process holds development-scoped credentials of its own, and the one act of Bob's per credential is issuing it once; creating and configuring a development repository, and a development change on the Cloudflare account, are then the process's acts, in the act table, never his.

**What is true today, measured** (#6, 29 Oct): a session's GitHub access is the Claude app's token in Bob's name, injected by the session's git proxy; on it the proxy refuses repository-settings writes (`403 Repository settings writes are not permitted through this proxy`, SETUP-STEPS) and repository creation in the organization answered 404 (#4), so the toy's repository and its two rulesets were Bob's hand acts on 29 Oct. The same proxy injects a Cloudflare API token for `api.cloudflare.com` in this environment: `GET /user/tokens/verify` answers `active`, and the token sees the account `Biocloudflare@neologic.com's Account` (id `20b53357…`); its scope is read with `GET /user/tokens/<id>` (X10). Nothing in a session's files or variables holds either credential (§8.8).

**BOB's details** (P17). The platform's way to give a session a credential is a **network secret on the environment**, per host, injected by the proxy after the request leaves the VM (§8.8; the environment's documentation, read 29 Oct): Bob adds it once in the environment's settings (the cloud environment menu in the session's title bar, then Edit, under Network secrets; where only environment variables are offered, a variable, which the tool reads by name), and every new session of every product on that environment carries it. So:

1. **GitHub**: a fine-grained personal access token of Bob's, for the host `api.github.com`, on all repositories of `believeinoakland` (so a repository the process creates is covered): Administration read and write (rulesets, settings), Contents, Pull requests, Workflows and Actions read and write, Metadata; with the organization's setting letting its members create repositories. Where only a variable is offered, its name is `NEOPROCESS_GITHUB_TOKEN`. Measured before the process relies on it (X9): whether a request to `api.github.com` carrying it passes the proxy with that token rather than the app's (the proxy replaces headers it injects), by `POST /orgs/believeinoakland/repos` for a throwaway repository and `POST /repos/…/rulesets` for its two rulesets, then their deletion; the result decides whether `proc repo setup` (below) is the route or the act stays Bob's with the reason measured.
2. **Cloudflare**: the token already injected; its scope read (X10) and widened by Bob only where a development act of the product's needs it (the product's `build/situations/` name the acts: deploys to a development account, R2 buckets for captures, workers). Measured on the first product act that uses it (X11).
3. **The tool**: `proc repo setup --repo <owner/name>` creates the repository (public, as the process is), makes the two rulesets (`tranche`: no force push, no deletion; `main`: a pull request required), enables nothing else, and reads them back (`GET /repos/…/rulesets`) as its proof; SETUP-STEPS then holds Bob's steps only as the fallback the measurement decides. `proc shims` runs on the new repository as today. Both acts join `tools/acts.md` (`create_repository(process token)`, `rulesets(process token)`), with X9's measured result.
4. **Partition**: the tokens are development-only, on Bob's development accounts; releases and anything a customer would guard stay outside them (§6); a token's scope is named here, and a widening is Bob's.

The handoff's list of Bob's acts shrinks accordingly: issuing a token once, instead of every repository's creation and rulesets.
