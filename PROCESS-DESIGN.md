# The process principles

**Status** · In force. Approved by Bob. History: `HISTORY.md`. These principles REPLACE the current process wholly; nothing in the old process survives unless it is derived from them. Their home is this repository, `believeinoakland/civicos-process` (P2). The restore point before the replacement is the branch `snapshot/pre-refactor-2026-09-25`: its parents are every branch tip of that moment, all kept reachable.

**P1 · Purpose.** The process exists to put correct, working product behaviour that meets every defined requirement onto `main`. Nothing else is output. A rule, a record or a test has value only as far as it serves that.

**P2 · The process and the product are separate.** Each has its own correctness. The process is defined in its own repository. It keeps the product's **build state** in one subtree of the product repository, and only the process writes there. The build state holds the architecture (layers, modules, their order and dependencies), each module's requirements, the plans, and the record of jobs.

**P3 · The process is correct before it is used.** A meaningful flaw in the process stops all product work until the process is fixed and **certified**: the fix is checked against these principles, then proven on a small dry-run tranche. The process is never patched in reaction while it runs.

**P4 · The architecture is owned by BOB, with Bob.** BOB, working with Bob, defines the layers and the modules. Only BOB, with Bob, adds, removes or reorders the layers and the modules that carry product capability; the rest of the architecture is BOB's (P17). The modules are arranged in one **total order**. Each module belongs to exactly one layer. A layer's modules are adjacent in the order, and every lower layer's modules come before every higher layer's. A module may use the services of modules earlier in the order, and never of a module later in it. That is acyclic by construction. The declared use is checked against the actual imports, and a violation fails the build.

**P5 · Requirements are owned by BOB, with Bob.** BOB, working with Bob, writes each module's requirements:
- the services the module **provides**: each interface and its behaviour;
- the services it **uses**, named by module;
- the invariants it keeps;
- the product requirements and design sections it satisfies, cited by section.

Requirements may suggest an implementation but never require one. The module is free to choose and change its implementation. Because requirements are read whole, never scanned, they are concise and unambiguous. Only BOB, with Bob, changes a module's requirements. BOB communicates a change to a requirement, or to the interface of a provided service, to every module that uses that service.

**P6 · A module fits in one reading.** A module is sized so that one session can read, in full, its code, its requirements, and the requirements of the services it uses.

**P7 · Only module jobs change module code, and every requirement is proven met.** Every change to a module meets all of that module's requirements as they stand at that moment. **Every requirement is tested, and the tests confirm the module is fully compliant with it.** No requirement goes untested, and no test merely samples one. The tests check behaviour at the module's interface, never its source text. When a module, or a user of a module, finds an ambiguity in the definition of a service, BOB updates the requirements to remove it and to state the service as it now is. The module's tests then confirm compliance with the clarified text. **A mechanical change is one pass.** When the same change, needing no judgment, must be made across many modules (a word replaced; a sentence moved to the word table and read by its key; a test made to read a sentence from the word table instead of copying it; an import or call re-pointed to a module's own declaration), it is made in one pass by a worker in BOB's session while no job runs, not by one job per module. Before the pass is committed, every module it touched has its tests run in one full run, beside the checks and the regenerated artifacts. A module where the change needs a judgment is done by its own job in the same tranche, never skipped. The pass is recorded in a ruling naming every module it touched.

**A stale test is fixed without a job.** A test that disagrees with correct code and with its requirement is stale. BOB, or a worker whose change BOB reviews, fixes it in BOB's own session: test files only, never a source file or a requirement line. The module's tests and the tests of every module the change reaches pass, and the checks read clean, before it is committed; one ruling names each module, file and commit. A change to product code stays a job's.

**P8 · The unit of work is the module job, except a mechanical pass (P7).** A module has at most one job at a time. A job applies every plan entry for its module. Flaws and improvements are both reasons to change a module. When the job finds either in its own module (a requirement not met, an inefficiency, a gap or error in its tests, a better way to meet a requirement, or anything else), **it deals with it in the job whenever possible**. It adds an entry to the next tranche only when it must.

**A cause job in a fix round.** In a fix round on a cut release, one cause whose fix spans several modules may be fixed by one **cause job** that holds every module the cause touches, when the reading set of those modules together fits one session (P6, P20); otherwise each module has its own job. A cause job is a module job for each module it holds: every change meets that module's requirements (P7), it runs each held module's tests and the tests of every module that uses what it changed, and its diff touches only the held modules' files. While it runs, no other job holds those modules.

**P9 · A flaw or improvement in another module goes through BOB.** A job that believes it has found a flaw in another module, or an improvement to it, reports it to BOB, described in terms of that module's requirements or its efficiency. BOB confirms it, then:
- if that module's job is running, BOB forwards it to that job, which deals with it in the job whenever possible and adds an entry to the next tranche only when it must, depending on its complexity and how far the job has gone;
- if no job is running for that module, BOB adds an entry to the next tranche.

A flaw in the requirements themselves goes to BOB and Bob.

**P10 · Builds happen in tranches, one layer at a time.**
- A tranche's plan is fixed when the tranche starts in what its entries mean; work found while it runs is added to it. **Nothing found in a tranche waits for the next.** A flaw, gap or improvement is done by its module's running job; else in the START of its module's job in a layer not yet started; else, for a module whose layer has closed, in the tranche's **completion round**: after the last layer and before the release is cut, one job per such module, run concurrently, lower layers first where one uses another. A completion round needs no further approval.
- The tranche runs one layer at a time, lowest first. **All the module jobs of a layer run concurrently.**
- All the jobs of the current layer stay active until every one of them has recorded that it is complete.
- If a job communicates a change to another job of the same layer, through BOB (P5), that other job processes the change and signals completion again, even if it had already said it was complete.
- Only when every job of the layer is complete are those jobs archived and the jobs of the next higher layer started, concurrently.
- The one exception to freezing is a change to a provided service. BOB carries it to the modules that use the service, and those are in the same or a later layer, so their jobs in this tranche pick it up.
- When every layer is complete, the tranche's plan is archived and the next plan becomes current.

**P11 · Tests follow the architecture.** Each module has its own tests, and each layer may have layer tests. A job runs its module's tests and its layer's tests. When it changes what its module provides, it also runs the tests of every module that uses the change. **Because every job in a layer may run that layer's tests, testing lives in module tests wherever possible, and the effort needed to run layer tests is kept as small as possible.** The full regression runs only at release, or when Bob asks.

**P12 · Done means merged.** A tranche works on its own branch off `main`. This process never changes `main` while a tranche runs. Bob's UX design stream may land on `main` meanwhile; the tranche's close then merges `main` into the tranche branch (never a rebase) and re-runs the checks before the fast-forward. A job is done when its tests pass and its work is merged into the tranche's branch. A tranche is done when every job is merged and the tranche's branch is merged to `main`.

**P13 · Sessions are kept short.** A job session is short and single-purpose: it does one job, as a worker does one planning step, and ends. State lives in the build state, never in a long-running context. A session's cost grows with its context size multiplied by its number of turns: re-reading its own context is most of what it spends. A long-lived session woken again and again with a large context is the most expensive thing the process can run. So BOB, which carries a tranche from step to step, refreshes when its context passes 40% of its context window; and ROOT is long-lived because each of its turns is small, so waking it is cheap.

**P14 · Usage is measured first, then bounded.**
- **The authoritative measure** is Bob's plan meter: the share of the weekly limit used, as Bob reads it.
- **The process measures TOKENS PROCESSED per session** (cache reads plus cache writes plus input plus output), tagged by tranche and job, and read by BOB from each session's archive. It never uses dollar estimates, which understate and are unreliable across container restarts.
- **The first tranches COLLECT METRICS; they are not bounded by them.** Token counts per job are recorded alongside job size (the module's lines, its entries, its test runs) and against the movement of Bob's weekly meter, to build an empirical model of what a job costs.
- **Real budget bounds are set only once that model exists**, and Bob approves them. Until then Bob sees each tranche's measured usage when it ends.

**P15 · A ruling is made once, and recorded unambiguously yet concisely.** A decision is recorded once, in its home document, stated unambiguously and as concisely as possible, so that every later session that reads it spends as little context as possible. It is not reopened without new evidence named in writing.

**P16 · Rules derive from principles.** Every process rule names the principle it serves. A rule is never added in reaction to an incident unless it can be derived from a principle. These principles change only with Bob's approval.

**P17 · Bob decides the high level; BOB decides the rest.** This working relationship is remembered and followed at all times, in all situations. Bob decides only high-level questions of **policy and doctrine, requirements, architecture and UX**. Every lower-level technical or detailed decision is BOB's, made without asking him: dependency edges, order within a layer, file ownership, helper and legacy modules, tooling, tests, branches, CI, the wording of a requirement, and every other matter of implementation or process detail. BOB decides it, records it once (P15), and reports it to Bob in plain words as done. A "with Bob" in any other principle or rule means only what is high-level by this principle. **Bob does not edit files and does not enter commands.** BOB does the work. When an act only Bob can take is needed (an action on his own account), BOB names that one act and walks him through it in plain steps. When BOB is unsure whether a question is Bob's, it decides by this principle and says which way it read it.

**P18 · The process is a pipeline.** While a tranche runs, BOB prepares the stages after it, so the next tranche can open the moment this one closes and no stage waits on work that could have been done earlier: the next tranche's plan; the requirements of the modules the next tranches will build, drafted, reviewed and brought to Bob where they are his (P17); the map of what each coming extraction moves out of a legacy module; and anything else a later stage will need. Preparation never changes `main` while a tranche runs, never changes a module a running job owns, and never changes requirements a running job is reading; it is written on the tranche branch, and changes the running tranche only through P9 and P10.

**P19 · Urgency.** BOB never decides, silently or otherwise, that the work may take longer than it must. Every tranche carries every entry that can safely be done in it; an entry is deferred to the next tranche only for one of three reasons: a decision of Bob's not yet made (P17); a deployment or measurement that cannot happen inside the tranche; something outside the product that does not yet exist. Never because of the order, a layer already closed, the tranche's size, a job's smallness, or because it changes no behaviour. Each deferred entry is named, with its reason, in the tranche's report to Bob. **A plan is written from the work that remains, not from the work that is queued**: it carries every entry that can safely be done in the tranche, and names the hard reason for each one it leaves out. The aim of every tranche is that the next one is needed only for work with a hard reason. The next tranche is prepared while this one runs and opens the moment it closes (P18); BOB never idles while work remains. Each tranche's report to Bob states its elapsed time, the work it finished (legacy lines removed, entries applied) and the work left. Speed comes from full scope and no idle time, never from weakening a safeguard: the layer order, complete test coverage and the checks stand.

**P20 · Read in full, never scanned.** Everything a session must read for its work is read in full. A skim, a search in place of reading, or a summary that drops what the work needs is a scan, and scans are forbidden: silent scans are silent killers of good development results. So documents and reading sets are kept small enough for one session to read whole, and the process scales its reading as the work grows: a document is trimmed or split, and where a body of work is still too large, helpers that are told the work, and what comes after it, read it in full and write the summary that work needs. BOB brings it to Bob only when a reading set stays too large and BOB cannot find a way to fix it, with what it tried and a recommendation.
