**Why a session does none of it** (measured 29 Oct, #5 and #8; PERMISSIONS §9). Whatever token it is given, a cloud session cannot create a repository or write its settings: the agent proxy injects the Claude app's token for the GitHub API, binds every call to the session's configured repositories (`POST /user/repos` 403, the proxy's own message) and refuses settings writes (`403 Repository settings writes are not permitted through this proxy`); the GitHub MCP server's create answers GitHub's 403 for the app (`Resource not accessible by integration`). A session can read everything back (`GET /repos/<owner>/<repo>/rulesets` on an attached repository), which is how `proc repo setup` verifies the act.

**The one act, once, for every repository (Bob).** The process repository's workflow `repo-setup.yml` creates a repository and its two rulesets on GitHub's runner with a token of Bob's, held as that repository's Actions secret; `proc repo setup` prints its dispatch from any session on the process repository, and run again reads the result back. One token covers every project, present and future (Bob, 29 Oct). The steps, from GitHub's own pages (docs.github.com: managing your personal access tokens; using secrets in GitHub Actions; permissions required for fine-grained personal access tokens; read 29 Oct):

1. Click your profile picture in the upper-right corner, then **Settings**. In the left sidebar click **Developer settings**; under **Personal access tokens** click **Fine-grained tokens**; click **Generate new token**.
2. **Token name**: `neoProcess`. **Expiration**: the longest offered (GitHub lets a token live without expiry unless a policy forbids it; GRANTS §3 renews before 14 days remain). **Resource owner**: your own account, the one that owns the process's repositories. **Repository access**: **All repositories**, so the repositories the process creates later are covered without a new token.
3. Under **Permissions**, open **Repository permissions** and set **Administration** to **Read and write** (GitHub lists `POST /user/repos` and `POST /repos/…/rulesets` under it: the acts of today); and, so the token is issued once for the configuring acts PERMISSIONS §9 names later (a development repository's workflows, environments and secrets), also **Read and write** on **Contents**, **Pull requests**, **Workflows**, **Actions**, **Environments** and **Secrets**; **Metadata** reads as **Read-only** by itself. Nothing else. Click **Generate token** and copy the token: GitHub shows it once.
4. Open the process repository's page on GitHub; under its name click **Settings** (open **More** first if it is hidden). 2. On the repository's page click **Settings** (under the "…" menu next to the tabs if hidden), then on the left **Rulesets**, **Rulesets** again, **New ruleset**, **New branch ruleset**.
