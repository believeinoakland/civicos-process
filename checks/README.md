# The five checks

PROCESS-MECHANICS §8: the only process tooling. Each takes the product repository's root and reads what is committed there (`git ls-files`), never a local build. Node 20 or later, no dependencies.

**Certification harness** (`checks/cert/`, `dryrun/cert/SUITE.md` §4; bio K164; not one of the five checks, a test tool for revising them and the mechanics):
- `node checks/cert/records.mjs [--strict] <file> ...` validates job records, the plan's Status line, handoffs, metrics CSVs and files of message first lines (`--message '<line>'` for one line); `--strict` requires the K164 grammar exactly (mechanics §6, §10, §13): envelopes with ids, `re` and `replaces`; the record Status with `sent`/`handled` marks; Size lines naming their session; the plan Jobs line marks; the backstop line.
- `node checks/cert/assert.mjs <run.json> [product]` judges a run's scenarios from git, records, CSV and snapshots: `<id> PASS|FAIL|UNOBSERVED <reason>`, exit 1 on a FAIL or a required UNOBSERVED. Predicates so far: A4, A5, B2, D3, D4, D6, D7 (X16), D9, E1, G4, H6.

`node checks/run.mjs <product>` runs format, architecture and coverage, channels when the product has `build/channels.md`, and words (`checks/words.mjs`, §8.6, bio K3923) when the product has the word table `docs/development/ux-substrate/screens/words.json`; a product without them is unaffected. Each check ends with one summary line; it exits 1 on any failure. The checks' own tests: `node --test checks/test/*.test.mjs`.

## The words check, two readings (D15, 2026-10-18)

- **Stitched sentences.** In a module's own product source, a `+` chain with a string literal and a non-literal operand, whose literals joined in order with `{}` for each non-literal operand pass `isSentence` and one literal of which has 3 or more words of its own (so `head + '## Session Log' + tail` is scaffolding, not a sentence), is one `inline` failure tagged `stitched`, at the chain's first line; its literals are not reported again. The chain is found on tokens (`stitchedChains`): cut at `, ; = ? : & | < > !`, `+=`, `return`/`throw` and the like, and at any bracket; a bracketed group, call or member access is one non-literal operand. Limits: no operator precedence (`a + b * 'x'` is one chain); `?:` branches and `||` alternatives are separate chains; a numeric `+` beside a literal reads as concatenation.
- **Developer messages (BOB's ruling, P17).** A string given to a built-in error constructor (`Error`, `TypeError`, `RangeError`, `SyntaxError`, `ReferenceError`, `EvalError`, `URIError`, `AggregateError`) is developer text, not a failure; member-facing refusals are codes read by key (DEC-83). The summary counts them as `dev <n>`. A custom `*Error` class stays tagged `?`.

## Words B: `t(id, en, vars)` (bio K3930, words-B-design §10)

- A bare call `t(…)` in a file that imports the specifier `t` from setup-words (`import { t } from '…/setup-words/index.mjs'`) is a reading; any other binding of `t` (node:test's `test as t`, a default import, a local helper) is neither a marker nor a reading, and member calls `.t(` are not judged: its id and en literals are never `inline` or `testcopy` findings, and a `t` id needs no row in `words.json` (`missingkey` still judges `word`, `hasWord` and `wordsOf` only).
- **`marker`** fails a `t` call whose id or en is not a plain string literal (a template with no placeholder is plain), whose id is not `KEY_RE`, whose id is used with a different en elsewhere in the tree (each place after the first), or that sits in a drawn-screen module (not in setup-words itself, which tests the refusals; `DRAWN_MODULES`: `screens-*`, `interface-shell`, `wizard-scripts`, `site`, `installer`, `installer-steps`). The summary counts `marker n`.
- **`--release`** (`node checks/words.mjs <product> --release`, or `checkWords(root, only, { release: true })`): also one failure `unreviewed <module> <file>:<line> <id>` per row of `bio-plane/src/setup-words/words-unreviewed.json`. `run.mjs` never passes it; it is for the release cut.

## The fixtures check, DRAFT (bio K4990, K4993 (2), K4995, K4996; not in `run.mjs` until Bob approves its text, K1258)

`node checks/fixtures.mjs <product> [module ...]` (`--list`: every candidate with file:line, its provider and the modules the file imports, for reading workers; always exit 0). It reads every JS/TS file under a module's `tests` and under test-support's `paths`, and the `paths` of every other module as source. Three classes, each failure `<class> <user> <file>:<line> [tag] <excerpt> -> <provider> (earlier|later|mixed)`:
- **answer**: an object literal of another module's shape: `ok: true|false` with `reason`/`detail`/`refusal`/`error`/`failure_class` (`refusal`), with `done`/`final`/`outstanding`/`waiting_on` (`owed`), or an `extent: { kind` (`extent`). Not an assert/expect argument (an expected value); not a literal whose `reason` code only the user's own source gives; tag `invented <CODE>` where no source holds the code.
- **stub**: a name of the form `*Stub`, `*Fake`, `*Double`, `fake*`, `stub*`, `double*` (once per file and name: `decl`, `import` or `use`), or a function standing in (`x.name = `, `name: () =>`, `name() {`, `function name`) for `registerJob`, `readHeld`, `armJobs`, `owedLater`, `keepLater`, `deliver`, `partsOf` and the audit's other seams (`INTERFACE_NAMES`) that the user's own source does not define.
- **code**: an UPPER_SNAKE literal at a `reason`/`code`/`error`/`failure_class`/`refusal`/`why` position that no source file holds (never accepted).

**Provider.** A code: the modules whose source holds it. A stub name: where it is declared or imported from (`jobRegistrarStub` stands for `registerJob`); a stand-in: the modules that define the service. Order is the array order of `build/modules.json`.

**The contract marker (K4995).** A hand-built answer or stub is accepted only when its provider is later than its user and a test of the provider runs it. The user writes `// fixtures-contract: <provider> <id>` on the candidate's line or up to 8 lines above it (the nearest marker above covers it); a file under the provider's `tests` writes `// fixtures-run: <user> <id>`. Failures by tag: `contract-not-later`, `contract-no-run`, `contract-unknown-provider`; class `contract`: `idle` (a marker covering nothing), `orphan-run` (a run no user marks).

**Tightening (second pass).** (1) `extent` counts only inside a stub or double's body or value, or as the argument of a call of one; extent data passed in is not an answer. (2) A refusal/owed literal that is a direct argument of a member call (`w.lib.x({...})`) or of a helper imported from another module (provider or harness) is an input; `Response.json`, `resolve`/`reject`, and calls of a stub or listed seam still build answers. (3) **Platform doubles are never stubs** (`PLATFORM_DOUBLE`): `FakeDate`, `fakeBinding`, `alarmDouble`, and fake/stub/double (prefix) or Stub/Fake/Double (suffix) of Date, Clock, Timers, Now, Fetch, R2, DO, KV, Bucket, Binding, Alarm, Storage, Miniflare, Workerd, Crypto, Random, Sleep. (4) A bare local `stub`/`fake`/`double` counts only where its value or `stub.name =` assignments name another module's exported name of 6+ characters (`spy standing in <name>`) or a listed seam. (5) A code literal the file both feeds in and asserts is pass-through data: allowed.

**Known limits (heuristics, for the reading workers).** a provider is `?` when no code or definition names one; a platform double with a name outside the allowlist is a candidate. Tests: `checks/test/fixtures.test.mjs`.

## How the checks read the build state (BOB #38, 2026-09-26)

- **Owner.** A path ending in `/` owns everything under it; any other path owns that one file. When paths nest, the most specific owns the file (a legacy module's `bio-plane/test/` holds the extracted modules' `bio-plane/test/m/<module>/`). Two modules claiming the same path is a format failure. This is how "exactly one owner" (P4, mechanics §1) is read.
- **Not product.** `not_product` in `modules.json` lists the paths no module owns (docs, the build state, the old tooling, release output). An import of one of them from product code fails.
- **Imports.** Relative specifiers of `import`, `export … from`, `import()` and `require()` in `.mjs`, `.cjs`, `.js` and `.ts` files, with comments removed. Package imports are not judged. A relative import naming no tracked file is counted, not judged: it is fixture text more often than code, and a real one fails when loaded.
- **Requirement ids.** An id is defined where it is written in bold, `**Rn**`, anywhere on its line; a mention elsewhere is plain `Rn`. A line carrying `*(retired` marks its ids retired, and they need no test.
- **A test names an id** by writing it as a word (`R12`) in a file under its module's `tests` paths, conventionally in the test's title.

## The protocol model (bio K164, `dryrun/cert/SUITE.md` §4.3)

`node checks/cert/model.mjs [--rules current|revised] [--set <bound set>] [--<bound> n ...]` explores the process protocol exhaustively (BFS) and prints, per invariant, PASS or the shortest counterexample; exit 1 on any violation. The engine is `model.mjs`; the rules are `rules-current.mjs` (the mechanics as written, each action citing its §) and `rules-revised.mjs` (the K164 revision; every property holds). Each rule set lists its bound sets; the default run explores all of them in under a minute. `--off <rule,…>` switches a revised rule off (negative controls only). Not one of the five checks: it certifies the mechanics, not a product.
